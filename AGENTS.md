## fitflow

Single-user fitness tracker: workouts, generated daily menu, weight, digestion, supplements. Angular 22 (standalone, signals), Chart.js, Vitest. Data lives in browser localStorage for guests; a signed-in user's data lives in Supabase (the browser keeps a copy that is written only after the backend accepted a change). BMAD planning output goes to `_bmad-output/`.

## Policy

- Do not change exercises, progression increments, phase/RIR limits or `SAFETY` text in `src/app/core/data/program.ts` and `ProgramService.phase()` without the user's explicit approval — they encode post-surgery (varicocele) loading caution. Propose the change instead.
- Supabase holds authentication (2026-10-07) and the data migrated since: profile, settings, weekly plans, foods, and (2026-10-09) days, weights and exercise history. Migrate any other data only when the user says so; keep every read/write behind `StoreService` / `DataSyncService` and a repository port so the swap stays in one place. Do not add another backend (no Firebase) or Supabase Storage without asking. Supabase Realtime is approved (2026-10-09) for when live updates are needed, but only behind a port with the SDK in the adapter, so a NestJS move stays an adapter swap (`backend-migration-rules.md`, rule 12).
- Ask before adding a runtime dependency to `package.json`.

## Where things are

- Persisted state shape: `AppState` in `src/app/common/interfaces/state/app-state.ts`; owned by `src/app/core/services/store.service.ts`.
- Height, starting weight, age and sex (`Settings.height` / `startWeight` / `age` / `sex`; `StoreService.bodyBasicsKnown()` needs all four) have no default: they differ per person. They are `null` until the user enters them; for a signed-in user they live in `profiles` (`height_cm`, `start_weight_kg`, `age`, `sex`; `AuthUser.height/startWeight/age/sex`, `AuthService.setBodyBasics`) and `BodyBasicsSyncService` (created at app start) keeps the local copy in step: at sign-in the account wins (when the account has none, the local values are dropped and the user is asked); saving goes to the account first (`BodyBasicsSyncService.persist`) and the values are written locally only when it accepted them (a failed save shows an offline / server error and writes nothing); guests keep them only in localStorage; a signed-in user gets the non-closable `BodyBasicsDialog` (`App`) while `StoreService.bodyBasicsKnown()` is false, a guest is never blocked and sees `<app-body-basics-form>` in place of the numbers that depend on them (body page, dashboard body card). Anything computed from them (BMI, …) must handle `null` and stay hidden.
- Safety: `bodyIssue()` in `core/targets.ts` (under 18, or BMI below 16 on the newest weight) makes `StoreService.bodySafetyIssue` non-null; then there is no target suggestion, and the dashboard shows a "see a doctor" notice instead of the menu, calorie / protein cards and meal timeline (`menuAllowed()`). Such a person also gets no generated menu or built-in program: `StoreService.effectiveMenuMode` / `effectiveWorkoutMode` become `trainer` (the plan they write themselves) whatever the settings say, so code that decides how a menu or workout is made reads those, never `settings().menuMode` / `workoutMode`. Do not add a path that shows a menu or calorie target without checking it.
- Targets: `Settings.targetMode` is `auto` (new users) or `custom` (settings saved before it existed, or chosen). In `auto`, `TargetSyncService` (created at app start) keeps `settings.kcalTarget / proteinTarget` equal to `suggestTargets` of the body data, newest weight and goal and rebuilds stored menus that no longer fit (`DayService.refreshMenusForTargets`); everything else just reads those two settings. The menu generator is pinned for 1500–4000 kcal and 3–6 meals in `menu.service.spec.ts` (three meals only up to 3000 kcal); `balance()` scales the portion caps with the target (`smaller` / `bigger`) and drops protein items when a small protein target cannot otherwise be met.
- Calorie and protein targets are suggested, never forced: `core/targets.ts` (`suggestTargets`: Mifflin-St Jeor × 1.55, goal lose / maintain / gain from `Settings.goal`, no weight loss below BMI 18.5) feeds the "suggested targets" box on the settings page; the user applies it and can still type their own. The menu generator reads only `kcalTarget` / `proteinTarget`.
- A new user (guest or account, nothing saved yet) starts with menu mode `auto` and workout mode `program` (`DEFAULT_SETTINGS`); the trainer plans are opt-in. Settings already saved in the browser keep their value.
- Settings of a signed-in user live in the account too (`profiles.settings`, a jsonb document with every synced setting; the body data has its own columns and `guestNoticeDismissedAt` is not synced). `SettingsSyncService` (created at app start) applies the account's settings at sign-in (the account wins; defaults for what it does not hold, a browser's settings are not copied in; the complete set is then written back) and sends the complete set with every later change; guests keep them in localStorage. A new `Settings` field is synced automatically (give it a default in `DEFAULT_SETTINGS`); one that must stay per device goes in `NOT_SYNCED` in `settings-sync.service.ts`.
- Weekly trainer plans (`AppState.weekPlans` for meals, `workoutPlans`): a guest keeps them in localStorage; for a signed-in user they live in the Supabase table `trainer_plans` (one jsonb row per user, kind and week) through `PlanRepository` (port; `supabase-plan.repository.ts` the adapter). `PlanSyncService` (created at app start) loads them at sign-in and at every app start with a session (the account replaces the browser's plans, a guest's are not uploaded). Saving or clearing goes to the account first (`PlanSyncService.persist`) and the page writes through `TrainerPlanService` / `DayService.setWeekPlan` only when it said yes, so a failed save (offline, server error) leaves localStorage untouched and two devices cannot drift apart. Code still reads them through `TrainerPlanService` / `StoreService` only.
- Day orchestration (plan creation, timeline, score): `src/app/core/services/day.service.ts`.
- Meal foods: calories and macros of an item are always worked out by `itemMacros` / `mealMacros` / `menuTotals` in `core/nutrition.ts` (a food of the reference list × its amount, or a typed-in item with its own numbers). A meal of the weekly trainer plan holds its foods as `MealItem[]`, edited with `<app-meal-items>` (`shared/meal-items/`); a meal that only has a name carries one placeholder item (all 0), which `realItems()` leaves out of the editor.
- Days, weights and exercise history (`AppState.days` / `weights` / `history`): a guest keeps them in localStorage; for a signed-in user they live in the Supabase tables `days` (one jsonb `DayRecord` per day), `weights` and `exercise_history` through `UserDataRepository` (port; `supabase-user-data.repository.ts` the adapter, `fake-user-data.repository.ts` for specs). Every change goes through `DataSyncService.commit()` / `commitDay()` (`core/services/data-sync.service.ts`): for a signed-in user it is sent to the account FIRST (one request, the function `apply_user_data`, one transaction) and written to the state / localStorage only when the backend accepted it; a failed save (offline, server error) changes nothing and shows an error. Changes run one after another, so quick taps never overwrite each other. The methods of `DayService` / `WorkoutService` / `BodyService` that change these are therefore async (`Promise`); a component that needs the result awaits it, and a field never sends a request while the user types: the weight / reps fields of the workout keep a draft in `WorkoutService` (memory only, shown through `fieldValue`) that travels in the same request as the next change of that day (a set ticked, an exercise completed, a set added, the workout saved). Other free-text fields that save on their own use `(change)`, not `(input)`. Every control that causes such a change shows a loader while it waits: `<button [appBusy]="BUSY.water(k(), ml)">` (`common/directives/busy/`, keys in `core/busy-keys.ts`, passed to `commit` / `commitDay` by the service as the busy key; styles for `[aria-busy]` in `styles.scss`). A new control that saves days, weights or history gets a key in `BUSY` and the directive. At sign-in (and every app start with a session) the account's data replaces the browser's; when the account holds none yet, the browser's data is uploaded once. `commit` may change `days`, `weights` and `history` only. "Delete all data" and a restored backup go through `DataSyncService.clearAll()` / `replaceAll()`.
- Static catalogs (foods, meal templates, exercise program, tips): `src/app/core/data/`.
- Reference lists ("Soraqçalar", `features/references/`): the data behind a select. `/references` is a grid with one card per list, driven by `REFERENCE_LISTS` in `reference-lists.ts`; a card opens `/references/<id>`. A new list = one registry entry, its own page and route, and a service owning its data; never put a list directly on the index page. Today only the food database (`food-references.page.ts`); system entries and a signed-in user's own come from the Supabase table `foods` through `FoodRepository` (port; `supabase-food.repository.ts` is the adapter), a signed-in user can add, edit and delete their own foods and drag every food (system ones too) into their own order (table `food_order`, read through the view `food_list`, changed by the function `move_food(id, target)`; the list request orders by that place), guests can only read the system foods (adding needs a sign-in; there is no local copy of user foods), and if the backend is unreachable the built-in `data/foods.ts` list is shown. `FoodCatalogService` owns all of this and is created at app start. It publishes the system foods to `systemFoods` in `core/food-book.ts` (the copy saved in `AppState.foodCache` at start, the live list once read); the menu generator, `itemMacros` and `itemName` read the food book through `foodOf` / `foodNameOf`, and `data/foods.ts` is only the last-resort copy for a first visit without a connection. New meal items are built with `foodItem()`, which copies unit and macros into the item (snapshot), so saved menus never change with the food list. Changing a system food (including its generator fields role/step/min/max) is a new migration in `supabase/migrations/`; keep `data/foods.ts` in step as the fallback copy. Entries carry `isSystem`, system ones can never be deleted, and user foods have `names` per language so backend data of that shape can replace the system part later. The menu generator reads only the system foods (the food book); a user food is added to a meal as a self-contained item. Selects driven by code behaviour (meals per day, menu/workout mode, theme, language) are not reference lists.

## Running and verifying

- `ng` is not on PATH; use `npx ng …` or the npm scripts.
- Run tests once with `npx ng test --watch=false`; `npm test -- --watch=false` fails under npm 12 (`Unknown cli flag`).
- After touching `MenuService`, `data/foods.ts` or `data/meals.ts`, run `menu.service.spec.ts` — it pins every generated day to 2600–2800 kcal and 170–190 g protein.
- Never run `prettier --write` on existing files — the code is hand-formatted and matches no `printWidth` in `.prettierrc`, so it rewrites whole files. Match the surrounding formatting instead.

## Conventions that differ from defaults

- Change state only through `StoreService.mutate()` (settings, plans and the like) or, for days, weights and exercise history, `DataSyncService.commit()` / `commitDay()`, called from a service in `core/services/` — never from a component, never by writing `localStorage` directly.
- Edit only the draft passed to the `mutate` callback; it is a `structuredClone`, and every `computed` depends on getting a new reference.
- A new `AppState`, `Settings` or `DayRecord` field needs a default in `StoreService.normalize()` / `DEFAULT_SETTINGS` / `newDay()`; keep the `fitflow.v1` key — existing data and JSON backups load through it.
- Business rules (progression, menu scaling, score, bloat triggers, body advice) live in `core/services/` or the pure helpers in `core/nutrition.ts` / `core/utils.ts`, not in components; a change to one gets a test in the co-located `*.spec.ts`.
- Dates are local `YYYY-MM-DD` keys built with `DateU` (`core/utils.ts`), weekday 1 = Monday; never derive them from `toISOString()` (UTC shifts the day).
- Only `az.json` is in the first bundle; `en.json` / `ru.json` are loaded on demand by `loadLang()` (`core/i18n/translate.ts`): an initializer loads the saved language before the first screen and `I18nService` loads a language before switching to it. Code that sets `activeLang` itself must `await loadLang(lang)` first; specs get both through `src/test-setup.ts`. Keep the initial bundle under its 500 kB budget (it was 584 kB with all three languages in it).
- Display options (gear panel in the header, `features/appearance/`): skin, direction, nav layout, text size, corners, contrast, clock and date format are `Settings` fields (synced like any setting) applied by `ThemeService` as attributes on `<html>` (styles in `styles/_skins.scss` and `_appearance.scss`). So write font sizes in `rem` (`text-[0.8125rem]`, never `px`), radii as `rounded-[calc(var(--r)_*_Npx)]` / `calc(var(--r) * Npx)`, and show times and dates through `fmtTime` / `| time` and `DateU` (they follow the clock and date format); stored times stay `HH:MM` 24 h.
- Text packs (`TextPack` in `core/i18n/translate.ts`): `admin.*.json`, `plan.*.json` and `supp.*.json` hold the texts of lazy areas (admin pages, weekly plan, supplements) so they stay out of the first bundle (it has a 500 kB budget). The route guard of the area loads its pack (`permissionGuard(id, { pack })`); a text used outside that area stays in the main files. New texts of a pack area go into the pack files (all three languages), not into `az.json`/`en.json`/`ru.json`.
- User-facing text goes through `t('area.englishName')` / `| t` (`core/i18n/translate.ts`); every text is a named key in the flat maps `core/i18n/{az,en,ru}.json`, Azerbaijani being the source language. Built-in content (foods, meals, tips, exercise notes, phases) keeps its Azerbaijani text in code and saved menus; it has keys with a content prefix (`food.`, `meal.`, `tip.`, …) and is translated at display with `td()` / `| td`. A new text needs its key in all three JSON files (`translate.spec.ts` checks this). Identifiers and comments stay English.
- Components are standalone, `OnPush`, with inline templates and `inject()`; a new page is a lazy `loadComponent` route plus a `NAV` entry in `app.routes.ts`.
- Form controls come from `shared/forms/`, built on Angular Aria (`@angular/aria`) with CDK Overlay (`@angular/cdk`) for the popup: dropdowns use `<app-select [label] [options] [(value)]>` (options are `{ value, label }` with the label already translated, so build them in a `computed` that calls `t()`), times use `<app-time-picker [label] [(value)]>`. Never add a native `<select>`, and do not write another custom popup; extend `shared/forms/` instead. Tabs use `ngTabs`, multi-choice toggles `ngListbox [multi]`. Aria has no checkbox or text input, so those stay native `<input>`; a custom checkbox-looking button needs `role="checkbox"` and `aria-checked`.
- `@angular/aria` and `@angular/cdk` add about 100 kB to the bundle. Keep them out of the initial chunk: a component that uses `app-select` / `app-time-picker` and sits in the app shell (`app.ts`) goes in a `@defer` block; page components are lazy routes and are fine. `bundle initial` has a 500 kB budget.
- Paged tables (backend lists): `PagedQuery` + `pagedResource` in `core/paging.ts` read one page through `httpResource` (a new page / size / search cancels the running request; the search is sent from 3 characters on; sizes 10 / 50 / 100) `<app-data-table>` in `shared/table/` is the table itself (columns as data, `appTableCell` templates for custom cells such as row actions; `reorderable` adds a drag grip (on the rows `canDrag` allows), also moved with ↑ ↓, and reports `reorder` for the owner to save) and `<app-pagination>` in `shared/pagination/` is the footer. The repository port supplies `request(p)` / `parse(...)` (see `FoodRepository`); `supabaseRestInterceptor` adds the key and session token to Supabase REST calls. Today only the food list (Soraqçalar) uses it; when the backend cannot be reached the page falls back to `pageSlice` on the in-memory list. A new paged table: add `request` / `parse` to its repository port and adapter, then use the same three pieces.
- Header and modals: the app header is `sticky` and publishes its height as `--header-h`; anything else sticky under it uses `top-[var(--header-h,0px)]` and an opaque background (rounded corners and gaps must be covered, or scrolled content shows through). `ModalComponent` hides the page scrollbar by setting `overflow` on `<body>`, never on `<html>` (that would make `<body>` its own scroller and the sticky sidebar scrolls away).

## Known pitfalls

- Settings of a signed-in user are sent after the local change (`SettingsSyncService`, a failed upload is silent), unlike plans, body data and the data of `DataSyncService`, which are saved to the account first. Do not assume "account first" for every setting.

## Backend migration (kept outside the managed block)

Follow `_bmad-output/planning-artifacts/backend-migration-rules.md` (Supabase first, adapter-only SDK use, plain Postgres, so a later NestJS + Postgres move is an adapter swap). Authentication is built and the data migration is under way (days, weights and exercise history moved 2026-10-09); a write goes to the backend first and to localStorage only after the backend accepted it. Do not migrate more data before the user says so.

Authentication (guest mode stays: no route requires a login, a notice tells guests their data lives only in this browser):

- `core/auth/`: `AuthService` is the abstract port, `supabase-auth.service.ts` the only file that imports `@supabase/supabase-js` (loaded with a dynamic `import()`), the provider is chosen in `app.config.ts`. State is `AuthStore` (signals); pages and guards use the store, never Supabase types. Errors become `AuthError` codes (`supabase-errors.ts`) and are shown through `auth.error.<code>` texts, never the backend message.
- Username or e-mail login goes through the Edge Function `supabase/functions/login` (the username → e-mail lookup stays on the server). Schema, RLS and triggers: `supabase/migrations/`; setup steps: `supabase/README.md`.
- Keys: `src/environments/environment.ts` (dev) and `environment.prod.ts` (production build) are committed; only the project URL and the publishable key go there. Never the service-role key.
- Roles and permissions: every page and action is a permission (`PERMISSIONS` in `common/interfaces/permissions/permissions.ts`, `<module>.<action>`, also the table `permissions`); a role (table `roles`, `role_permissions`) is a set of them; an account has one role (`profiles.role_id`, `AuthUser.roleId` / `permissions`; `null` permissions = unreadable, the default role applies). `PermissionService.can()` is what the UI asks (a guest has the whole app and no administration); pages are guarded by `permissionGuard('<module>.view')` in `app.routes.ts` and listed in `app.nav.ts` (`NAV` has a `permission`), edit parts of a page carry `appRequires="<module>.edit"` (`RequiresPermissionDirective`: inert + dimmed). This only guides the UI; the administrative actions (users `/admin/users`, roles `/admin/roles`, both only for roles that hold their `view`) go through `AdminUsersRepository` (port; `supabase-admin-users.repository.ts` calls the Edge Function `supabase/functions/admin-users`, which holds the service role, loads the caller's permissions and checks them on every call). `AdminUsersService` waits for the backend before it changes a list. Never put the service-role key in the app; a new admin action is a new action in that function; a new permission is a migration AND an id in `PERMISSIONS` (+ texts in `core/i18n/admin.*.json`).
- Profile page `/profile` (picture, username, password; reached from the avatar menu): the picture is a 160 px JPEG data URL in `profiles.avatar` (no Storage bucket), the password change re-checks the current password through the login function.
- Pages are in `features/auth/` under `/auth/*` and render without the app shell (`App.isAuthPage`).
